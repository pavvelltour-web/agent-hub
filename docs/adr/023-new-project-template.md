# ADR-023: `hub new` creates a project only in a new or empty folder, and its verify command stays unapproved

Context: `hub new <type> <folder>` and the wizard's "Новый по шаблону" create a skeleton (brief, architecture, `.gitignore`, `hub.json` with a `verify` command), the rules, the type's skills and a git repository in one step. Creating files in a folder the user names, running a program there and writing a command that later runs with the user's rights are each a security decision.

Decision (`src/core/templates.ts`, `templates/<type>/`, `src/cli/main.ts`, `src/server/api.ts` `POST /api/new/pick|plan|apply`, `web/js/views/welcome.js`):
- **Where.** The folder must not exist or must be an empty folder (a folder that holds only `.git` is not empty). Refused: a file, a link, a drive/filesystem root, a credential path (`secrets`, `.env`, ...), anything inside `~/.claude`, `~/.codex`, `~/.agents`, `%APPDATA%\Claude` or the hub home. Every check runs on the **real path**: the nearest existing ancestor goes through `realpathSync.native` (8.3 short names, junctions, case, `.` and `..`), the forbidden folders are resolved the same way, and `plan.root` is the real path. Paths that begin with two separators (`\\.\`, `\\?\`, `\\?\UNC\`, `\\host\share`, `//host/...`) are refused outright. (Observed before this fix: `C:\Users\<user>\CLAUDE~1\x` and `\\localhost\C$\Users\user\.claude\x` passed the string comparison.) The same check runs again at apply time, before anything is written, and apply also refuses when the real path is no longer the one that was planned (a junction inserted into the path since). The API accepts absolute paths only; picking a folder (`/api/new/pick`) only returns a path. `POST /api/new/plan` returns a digest of the type, folder, every file (path, action, text or link target), the steps and the verify command; `apply` needs `approved` and that digest (409 when the re-derived plan differs).
- **What.** One plan: the generic init plan (hub.json config, `toolkit.json`, `AGENTS.md` from `renderRules` with the type's section, `CLAUDE.md` pointer, `REVIEW.md`, skill links, lock) plus the template's files, shown in full and written through `applyPlan` (approval, backup, undo). Template text gets only `{{name}}` replaced. The template's `hub.json` is an overlay: only its `verify` (a valid argv list) is merged into the generated config; nothing else from it is trusted. The files are named without a leading dot where npm would drop them (`gitignore`), mapped to `.gitignore` in the plan.
- **One command.** The only step that runs is `git init -b main` in the new folder, as an argument array with the allow-listed environment (`minimalEnv`). `applyNewProject` accepts a step only if its argv and folder equal exactly that, so a changed plan cannot make it run anything else. No commit is made.
- **verify is not approved.** `planNewProject`/`applyNewProject` never write the approval store. The template's `verify` (a `node -e` check that `brief.md` and `docs/architecture.md` exist and are not empty: green on the empty skeleton, red when one is removed) runs only after the digest-pinned approval of the review/cascade flow (ADR-017). The plan says so.

Status: tests (`src/core/templates.test.ts`, `server.test.ts`) cover every refusal above, the plan per type (including a Cyrillic path with spaces), verify green and red on a real folder, `planVerify` reporting `approved: false` with no approval file written and `approveVerify` working only for the shown digest, the apply-time re-check, a tampered step list, the CLI (`--yes`, no terminal, non-empty folder, unknown type) and the API. The panel was checked in a browser against the demo server (a project was created end to end in a temp folder).

Known limits (accepted): the check-then-write is not atomic (a file that appears between the apply-time check and the write is overwritten, but `applyPlan` backs up every file it replaces first, so `hub undo` restores it); a link inserted between the apply-time check and the write is not noticed (the window is the time between two calls); the skeleton is not committed, so the cascade's verify needs a first commit by the user; a global `init.templateDir` in the user's git config is the user's own configuration.
