# ADR-025: using the leftover limit before a reset is opt-in per project, starts only what the user approved, and fails closed

Context: a subscription limit that resets soon is wasted if it is not spent. Phase 7.4 lets the hub offer low-risk work (a read-only review of old code, missing tests on a branch) for that leftover. The danger is the opposite of the saving: something that starts agent runs by itself, spends a limit the user needed, runs on a paid API key, writes to the main branch, or can be switched on by a file in a cloned repository or by a script that only has the panel's cookie.

Decision (`src/run/scheduler.ts`, `src/run/autouse.ts`, `src/run/autouse-wire.ts`, `src/server/phase7-api.ts`, `src/server/server.ts`, `web/js/views/autouse.js`, `web/js/autouse-model.js`):
- **OFF by default, per project, switched on only by a request from the panel's own code.** The switch lives in `<hub home>/autouse.json`, keyed by the project's canonical path. A project's `hub.json` is never read by the scheduler, so a cloned repository cannot enable anything (test: a `hub.json` that says `enabled` changes nothing, in the unit tests and in the HTTP test). A row only counts when `enabled` is the boolean `true`, with a root whose key matches; a loose or hand-made row, a wrong type, an oversized or unreadable file is "everything off". `POST /api/autouse/enable` needs (1) the session cookie, Host and Origin checks every route has, (2) `meta.userAction`: a same-origin `Origin` header AND the panel's own `x-hub-user-action: click` header, set by `server.ts` (another origin cannot send that header without CORS, and no CORS answer is ever given). This proves that the panel's code made the request, NOT that a human clicked: a script that holds the cookie can send both headers, and a request with no `Origin` header at all is still accepted by every route that does not read `meta` (all the GET routes and the older POST routes), (3) a typed confirmation: the project's folder name, compared exactly (NFC, trimmed) on the server as well as in the dialog. Every flip is appended to `<home>/autouse-audit.jsonl`. Switching off needs the click but not the word, and cancels every approval that had not started.
- **Nothing starts without an approved queue item.** The user approves one offer with a click (`POST /api/autouse/approve`, same click rule). The job is BUILT BY THE SERVER from `kind` and `agent` only (enums): the percent, `writes` and the prompt are never read from the request (test: a body with `writes: 'main'`, `prompt`, `permission: 'full'`, `root: '/'` is stored as `writes: 'none'`, no prompt, no permission). The prompts are fixed text in `scheduler.ts`. An approval lasts 48 h and is then dropped; a kind that is already approved or running is not offered again.
- **Every started run is an ordinary run.** `realAutoDeps` calls `RunManager.start` with a `StartReq` built by `startReqFor`: a review is `plan` permission with the `review` work mode (the runner keeps such a thread in plan); new tests are a `task` run (a worktree and a `hub/…` branch, never the main folder) with `edit` permission, so the result waits for the review gate and the user. No internal-only field (`extraArgs`, `isolatedCwd`, `autoContinue`) is ever set, `full` permission is never used, nothing is pushed (the push guard of every run applies), and the guardrails of ADR-026 apply to the start. `graph-refresh` is part of the job type but is not an agent run (it is the graph update of ADR-021): the scheduler never starts it.
- **Fails closed.** A job is suggested and started only when: the limit reading is KNOWN (a percent in 0..100, the limit not reached, a reset time in the future) and FRESH (older than 2 h counts as unknown: the readings come from CLI events and the history sync); at least 20 % is left; the reset is at most 24 h away; and after the job at least 10 % would still be left (jobs of one agent share one budget). Unknown is never "plenty". The expected percent comes from the user's own calibration (`estimate`, cautious p75 end); with no calibration (Claude before enough limit snapshots) the agent is not offered at all.
- **Subscription only.** `billingOk` refuses unless the CLI's own status answer is a recognised subscription login (`claude.ai`/`oauth`/`subscription` for Claude, `chatgpt` for Codex) and no variable that makes a CLI bill by the token is set (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY`, `CODEX_API_KEY`, Bedrock/Vertex/Foundry switches). An unknown or unrecognised login is a refusal.
- **Bounded and stoppable.** One run at a time, one start per tick, at most 3 starts in 24 h. Each tick re-reads the limit: a live auto run is stopped when less than 10 % is left or the limit cannot be read. The project must still be at the folder the user switched on (a moved or vanished folder cancels the item). A spawner that throws marks the item `failed-to-start` and nothing else happens.
- **Testable without time.** `AutoScheduler.tick()` is synchronous and takes the clock, limits, billing check, circuit breaker, spawner, stop and run state as functions; the tests use no timer. The only real timer is `startAutoLoop` (one pass a minute, `unref`-ed, never overlapping, never throwing, injectable `setInterval`), started by `hub ui` only: the scheduler works only while the panel process runs, and the panel says so. The history sync that refreshes the readings runs only when something is waiting, at most every 10 minutes (it reads the agents' folders read-only, as the panel already does).

Consequences and trust boundary: the trust root is the panel session (cookie + Origin + header). A local process that can read the browser's cookie jar and forge both headers could still flip the switch; that is the same boundary as approving a review check (ADR-017) and is not widened. What the scheduler can do once enabled and approved is bounded by what an ordinary task run can do, plus a token budget of one run per approval. It cannot spend on an API key, cannot run when it cannot read the limit, cannot write the main branch, and cannot be started by a file.

Status: red then green in `src/run/scheduler.test.ts` (thresholds 20 % / 24 h / 10 % margin, unknown and stale readings, hostile queue rows, default OFF with a hostile `hub.json`, one start per tick, TTL, daily cap, stop under the margin, toggle off cancels, moved folder, spawner that throws, hostile state file, the loop) and `src/run/autouse-integration.test.ts` (the real RunManager and fake agent: a review thread in plan, a worktree branch for tests, the main folder untouched), `src/server/phase7-api.test.ts` (click rule with every missing piece, typed word, server-built job, no double approval). The click-rule test was shown to fail when the check was removed.

Known limits (accepted, labelled): the words that recognise a subscription login are NOT verified against a signed-in CLI here (not signed in); wrong words only make the feature refuse. The limit readings are as fresh as the last CLI event or history sync; after 2 h without one the scheduler refuses (the loop syncs while something waits). The leftover is the share of whichever window the latest reading describes (weekly or five-hour): the offer says what is left and when it resets, and does not assume which. The expected percent is a range from the user's own history; a task that costs more than its p75 can pass the 10 % margin before the next tick stops it (one-minute resolution).

## Review fixes (after the Opus review of 7.3-7.5)

- **Only the WEEKLY reading counts.** The offer is about the weekly limit (the expected percent is a share of the week), so a reading is used only when its window length is KNOWN and at least 6 days. Claude's `rate_limit_event` carries `rateLimitType` (`five_hour`, `seven_day…`): it is now turned into a window length (300 / 10080; an unknown type gives none; the shape is NOT verified live, the CLI here is not signed in). Codex's rollout carries two windows: both `primary` and `secondary` are stored, told apart by their own `window_minutes`, not by their names. `limit_snapshot` rows of different windows live side by side (the duplicate check is per window), `limitSnapshots` returns the newest WEEKLY row per agent (a newer 5-hour row does not hide it, a row with no window length never counts), and the calibration (`calibrate`) uses weekly rows only. A reading with no or a short window is "unknown" and the scheduler refuses. The case that was found ("30 % used, resets in 3 h, no window length") is now refused, and a proper weekly reading still allows.
- **One scheduler per hub home.** `RunManager.isLive` knows only its own process, so two `hub ui` processes would each judge the other's run "not live". The loop now needs `<home>/autouse.lock` (`wx` create, owner pid and heartbeat; stale when the pid is dead or the heartbeat is older than 3 minutes; taken over by moving the stale file aside; a process re-reads it before acting and never ticks without it). Each started item records its owner pid. Process start time is not read (no portable way without running a program); the heartbeat covers a reused pid.
- **The project's own Claude settings.** The run starts in the project folder, where Claude Code would apply `.claude/settings.json` and `settings.local.json`: `env` (an API key or a base URL), `apiKeyHelper` (billing), `hooks` and `permissions.allow` (commands without a prompt). Scheduler-started Claude runs get `--setting-sources user` (documented flag, NOT verified live), and a folder whose settings hold any of those four is refused with the reason. The subscription check (`auth status`) is made from the project folder and with the environment the run will get. Codex's project config is not checked.
- **The opt-in follows the repository, not the folder.** Switching on records the first-commit sha of the repository; a different repository at that path drops the opt-in and cancels the approvals at the next tick (and an approval is refused).
- **Switching off or cancelling stops a live auto run** through the normal stop path (`RunManager.stop`), not only the waiting items.
- **Tamper evidence for `autouse.json`.** The hub keeps a hash of what it last wrote (`<home>/integrity.json`); a file that does not match, or one the hub never sealed, is not read: everything reads as OFF, the scheduler refuses, the change is written once to the audit log and to `tamper.json`, and the panel says «Файл настроек изменён не hub: проверьте» until the user resets (which drops what the file held).

### What an unattended agent can reach

An automatic run is an agent running as the user. Unattended edit mode can write anywhere that user can write, not only in its worktree: it can rewrite `<hub home>/autouse.json` or `config.json`, change `integrity.json` together with the file it sealed, or append a forged `rate_limits` line to a Codex rollout that the history sync then reads. NONE of the files of this ADR is a hard boundary against that, and the hash seal catches only a careless or naive change, not a determined one. What bounds the damage instead: the run is `plan` permission (reviews) or a worktree branch (tests) and is stopped by the circuit breaker (ADR-026); the user approves every job; and the limit readings are refused when old. Deny rules for the hub home and `~/.codex` were considered and NOT added: no flag could be verified here, and a shell tool can write anywhere regardless of a rule for the file-edit tools. The honest advice is to review the task branch before accepting it and to keep an eye on the audit lines.

## Second review round

- **The lock never replaces a live owner (B1).** The first version took a lock over once its heartbeat was 3 minutes old even when the owner was alive; the new owner then judged a run it did not host to be finished and started a second one while nobody watched the 10 % margin of the first. Now: (a) the heartbeat has its OWN timer (every 30 s, `unref`-ed, cleared by `stop`), independent of the tick and of the history sync; (b) the lock is taken over only when the owner's pid is not alive, or when a start-time probe says the live process at that pid started after the owner recorded (a reused pid); an alive owner is never replaced however old its heartbeat, and after 30 minutes of silence the panel says «Другой процесс hub держит планировщик» and this process stays idle (fail closed; a lock stuck on a reused pid is cleared by deleting `<home>/autouse.lock`; the default probe cannot read another process's start time, so it does not help there); (c) a started item whose owner is another LIVE process is never marked finished or replaced; (d) a clean stop releases the lock, and a takeover checks that the file it moved aside is the one it had checked (else it gives it back), so two simultaneous takeovers cannot both win.
- **Only the exact weekly window (S3).** `seven_day` is the overall week; `seven_day_opus`, `seven_day_sonnet` and any other type are sub-limits: no window length is recorded for them, so they are stored but never feed the weekly decision, the duplicate check or the calibration.
- **The project's Claude settings are an allowlist (S4).** A project `.claude/settings*.json` is accepted only when every top-level key is in a small safe set (`model`, `outputStyle`, `cleanupPeriodDays`, `includeCoAuthoredBy`, `spinnerTipsEnabled`, `$schema`, and `permissions` with only `deny` / `ask` lists of strings); any other key is refused and named (clipped, control characters removed); a project `.mcp.json` is refused. The check runs first in `GET /api/autouse`, before anything is spawned; the subscription check (`claude auth status`) is spawned from the project folder with `--setting-sources user` (NOT verified live: if that CLI rejects the flag on `auth status` the check fails and the feature refuses, the safe side) and with the environment the run gets (`agentEnv`). For `missing-tests` the COMMITTED file is checked (`git show HEAD:…`, because the worktree is cut from HEAD), with the repository-config guard of `agentConfigGuard`.
- **A flagged state file does not hide a live run (S1).** The loop remembers the run ids it started in memory and can find unfinished automatic runs in the run table (their fixed prompts); when `autouse.json` is flagged as changed it STOPS them through the normal stop path, and the Switch-off and Cancel routes stop them too, whatever the state file says. The seal file is now written under a lock (`integrity.json.lock`), the new content is sealed BEFORE it is renamed into place, and a reader retries briefly before it calls a mismatch tamper (a test with three processes sealing 210 keys at once loses none).
- **The opt-in is 'same history at the same path' (N2).** The identity stored is the first-commit sha plus the canonical root path (the key). A fork or a clone with the same history at the same path is therefore accepted, and a different history at that path drops the opt-in; this is deliberate and fail-safe, not a proof of which copy it is.
- **Upgrade behaviour (N3).** Files written by a version before the seals exist read as changed: an old `autouse.json` (so the automatic start is OFF until the user switches a project on again), an old `acks` file, an old `config.json` `guardrails` block (the defaults apply). Claude calibration rows without a window length go to `none` (no percent) until weekly readings accumulate.
