# ADR-022: the starter kit installs third-party skills into the hub library only, from named repositories, at one commit the user saw

Context: the first-run wizard offers a short list of skills (`registry/starter.json`). Installing them means fetching text from the internet that an agent will later treat as instructions, so what is fetched, from where, and where it lands is a security decision. The existing `hub get aitmpl/...` path (ADR on library installs, `src/core/install-remote.ts`) already shows the whole component first and only accepts what was previewed; this reuses that machinery and tightens it for a source that is a git repository.

Decision (`src/core/starter.ts`, `registry/starter.json`, `src/server/api.ts` `GET /api/starter`, `POST /api/starter/plan|apply`, `web/js/views/welcome.js`):
- **The list is data.** `registry/starter.json` is validated on load: safe ids, `owner/repo`, a relative safe path, a `ref` that is a 40-hex sha or a branch name (`latest` and `HEAD` are rejected), a mandatory `license` (the word `unknown` is allowed and means unchecked), a unique id, and a source type of `github` or `manual`. A `manual` source (a program installed by its own command, or a skill whose source is not pinned yet) is listed with its reason and is never fetched by the hub.
- **Where it may be fetched from.** The fetcher is built from the repositories named in the list: https only, no port, no credentials, no redirects (a redirect is an error), 20 s timeout, size caps. Only `api.github.com/repos/<repo>/git/ref/heads/<branch>`, `.../git/trees/<sha>?recursive=1` and `raw.githubusercontent.com/<repo>/<sha>/...` of a listed repository are allowed; a raw URL must carry a 40-hex sha, so a moving branch is never read as content.
- **One commit.** A branch `ref` is resolved to its sha when the user asks for the preview; every file is read at that sha. The preview shows the sha; the digest covers (id, sha, license, bytes of every file). Apply fetches again and refuses (409) when the digest differs, so what is written is exactly what was shown. A `ref` that is already a sha is used as is. This is trust on first use for a branch `ref`, bounded by the full preview and the digest, not a pre-reviewed pin (see Known limits).
- **What is accepted.** Only the folder `<path>/` of the commit: regular files (git modes 100644/100755); a symlink (120000), a submodule (160000/commit), a truncated tree, a file path outside `[\w.-]/` segments, `..` or `.git`, a name Windows cannot hold (NUL, CON, `:`, trailing dot, two names equal but for case; the review copy's `pathProblem` rule), a binary file (NUL), more than 40 files, a file over 200 KB or a skill over 1 MB are each a refusal of that skill with the reason. `SKILL.md` is required and its `name` must equal the starter id. Nothing is executed; a skill with scripts gets a note.
- **Where it is written.** Only `HUB_HOME/skills/<id>/` through `planStarter` → `applyPlan` (approval, backup of the previous state, undo, audit line). Never `~/.claude`, `~/.codex` or `~/.agents`. A folder that holds a file, or a skill of that name found anywhere on the PC, is skipped ("уже есть"), never merged or overwritten. If `HUB_HOME/skills` is itself a link the install is refused. A provenance file `.hub-source.json` (id, repo, path, commit, license) is written next to the skill.
- **License.** Unknown license means unchecked by default and a warning in the plan; a source the hub cannot fetch is unchecked too. The user can still check an unknown-license skill that the hub can fetch after seeing the warning. The license text in `starter.json` is a claim of the list, shown beside the commit, not verified against the repository's license file by the hub (a mismatch with a license named in `SKILL.md` is noted).
- **Trust.** Registry text, the fetched tree and the skill files are data: they are shown as text, never interpreted, and nothing in them selects what else is fetched (the file list comes from the git tree of the pinned commit, the host list from the shipped `starter.json`).

Status: the list rules, the fetcher allow-list, every refusal above, the single-commit/digest property, the plan paths, apply and undo, and the API (approval, digest mismatch, no write on plan) are tested with a fake GitHub. **Not verified:** a live fetch from GitHub, that the repositories and paths in `starter.json` exist and hold the license it claims (the three `obra/superpowers` skills match the local copy of that project's layout; the other four entries are `manual` because their source was not verifiable offline), GitHub's unauthenticated rate limit (60 requests per hour per address; a preview needs two API requests per repository plus one per file from raw).

Known limits (accepted): a branch `ref` is trusted at preview time, so a compromised repository branch is shown to the user as ordinary text and the user's reading is the control; set a sha in `starter.json` to remove that. The skill the user finally links to a project is later read by an agent: reviewing it is the user's step, the hub only refuses to hide what it installs.
