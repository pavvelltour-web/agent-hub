# ADR-024: the run trace and the context gauge read `turn` rows the hub stores per model call: numbers, names and times only, bounded everywhere

Context: Phase 7 shows what a run did step by step (tokens, prompt size, cache share, tool calls and their durations) and how full the context is while the user writes. Both need per-call numbers. ADR-018 deliberately did not store the per-call prompt size (the `context` event is only watched), and the `usage` event of a Claude run is the SUM of the run (the `result` line), so neither could answer "what did step 7 cost". The trace also must not become a second place where secrets or tool output live.

Decision (`src/adapters/claude.ts`, `src/adapters/event-utils.ts`, `src/run/runner.ts`, `src/run/trace.ts`, `src/server/api.ts`, `web/js/views/trace.js`, `web/js/trace-model.js`):
- **One parser.** The `context` event of ADR-018 stays the only place that reads `message.usage` of an `assistant` line (subagent lines, `parent_tool_use_id`, are still ignored). It now also carries the split of that call (`newIn` = input + cache writes, `cachedIn`, `out`) and the message id (`mid`), and is emitted FIRST in a line so that it opens the turn the line's tool calls belong to. The runner's watch (threshold, stop, warn) is unchanged.
- **What is stored.** The runner turns each `context` event into a `turn` row in `run_event` (numbers and the message id, rebuilt by `sanitizeEvent`: finite, whole, capped at 1e12). The Claude CLI writes one line per content block with the message's usage: lines with the same `mid` fold into one turn (the later line may carry the final `out`). A `turn` row is never sent to the panel stream and `RunManager.events()` leaves it out (the transcript, the chat log and the handoff card never see it); `seq` has a gap there, as it already has for `partial`.
- **Bounded storage.** At most `MAX_TURN_ROWS` (5000) turn rows per run; the first time the cap is hit the user gets one `warn` ("шагов больше 5000"). A hostile or runaway CLI cannot grow the log with them.
- **What a trace holds.** `buildTrace` reads `turn`, `tool`, `tool_result`, `usage`, `session` and `end` rows and returns names, numbers and times: per step the model, tokens, prompt size, cache hit `cachedIn / (newIn + cachedIn)`, price, and the tools (name, duration, ok, size of the output). It never returns a tool input or an output text. Tool names and the model are redacted AGAIN and capped at 100 characters on the way out (a row written before the sanitizer existed must not leak). `readTraceEvents` reads the rows with SQL that returns only the id and name of a tool and only the size in bytes of a result body: the 64 KB bodies stay in the database. At most 50 000 rows are read per trace (`truncated` says so); at most 100 tools are listed per step (`toolsMore` counts the rest); a page is at most 200 steps (`after` = last step number seen).
- **Honest numbers.** Durations are the hub's arrival times: a tool lasts from its call line to its result line, a step until the next step starts. That is inferred from the stream, not a stopwatch in the CLI, and the page says so. A tool with no result (the run was stopped) is marked `open`, never "ok". The price is `costUsd(model, tokens)` from the price table: an unknown model gives `null` ("неизвестна"), never 0; the run total is the CLI's own `total_cost_usd` when it reported one. A Codex run has no `turn` rows (no per-call prompt size is reported, ADR-018): a `usage` event closes a step and `context` is 0 = not measured. A run recorded before Phase 7 is one step holding what was recorded. Subagent calls are not in the trace (they are not in the `context` event either).
- **HTTP.** `GET /api/runs/:id/trace` (paged JSON) and `GET /api/runs/:id/trace.jsonl` (one JSON object per line: steps, then totals; `application/x-ndjson`, `content-disposition: attachment; filename="trace-<id>.jsonl"` with a validated id, `nosniff`). Same session cookie as every API call, GET only, id checked against `^r[0-9a-z]{2,40}$`. `Res` gained an optional plain-text body for the download; JSON stays the default.
- **Panel.** `trace.js` draws everything with `h()`/`textContent`; `trace-model.js` reads every field by type (never `String(x)`), turns control, bidi and zero-width characters into visible `\uXXXX` and caps names. The journal (`logs.js`) filters by project, agent, model and kind (`log-model.js`) and links each run row to «Подробно».

- **Context gauge (7.2).** `GET /api/runs/:id/context` (`src/econ/context.ts`, `web/js/views/context-gauge.js`, `web/js/context-model.js`) reads the same `turn` rows and writes nothing. A chat thread is the run and the runs it resumed (`resume_of`, at most 50, loops cut); the baseline is the FIRST call of the oldest run (a resumed run's first call already carries the earlier conversation), `used` is the newest call, `turns` counts calls over the thread; a handoff starts a fresh session and so a fresh thread. `contextBreakdown` gives system / rules / skills / conversation that always add up to `used` (an estimate larger than the measured first call is cut) and `turnsLeft` = steps (model calls, not messages) until 250K at the mean growth per step, null with fewer than two steps or no growth. Levels: amber from 200K, red from 250K, the same number as the runner's stop (`HANDOFF_AT` is the one definition; `CONTEXT_LIMIT` is that value); the panel colours come from the warning / danger tokens and a text chip says it too.
- **Window: from the price table only.** A price row may carry `window` (a whole number of tokens, 1 000 to 100 000 000; anything else is ignored and the row keeps its price). The bundled table names none, because no source for any window is recorded in this repository: so by default the gauge shows the number and «окно неизвестно», with no bar. A user can add `window` to a row in `<hub home>/prices.json`; an override row inherits a bundled window and a price edit made from Settings keeps the window the user wrote.
- **Rules and skills are estimates, and say so.** Rules = (size of `AGENTS.md` + `CLAUDE.md` in the run's folder) / 4: only `lstat` sizes are read, never the text. Skills = the skill-list estimate of the loading audit for that project and agent, cached for a minute (at most 50 entries). The panel writes «≈» and the bar tooltip says it.
- **Cache note, Claude only.** From 2 minutes after the last call the panel says «Кэш остынет через N мин», after 5 minutes «Кэш остыл: следующее сообщение дороже» (the plan's 5-minute TTL; not verified live, not claimed for Codex). The age comes from the server's clock at each poll and the panel keeps counting between polls. Nothing is shown while a run is live.

- **Review fixes (Opus review of 7.1/7.2).** (S1) The skills estimate never runs on the request path: `GET /context` asks `createSkillsEstimator().peek`, which answers at once with the last value (null before the first, reported as `skillsKnown: false`, never waited for or guessed) and starts ONE refresh per root and fingerprint in a worker thread (`src/econ/skills-worker.ts`: the same loading audit, away from the server's event loop, hard-stopped after 30 s, 256 MB heap). The fingerprint (time and size of the skill folders' `SKILL.md` files and of the files that switch skills on and off) is checked at most every 10 s, so a poll does not recompute; a failed or hung refresh keeps the old value and is not retried for a minute; the cache holds 50 roots and drops the least recently asked one. (S2) The gauge's timers are a DOM-free controller (`web/js/gauge-controller.js`): after `stop()` a late `show()`/`refresh()` or a late answer does nothing, a view that was on the page and left stops itself, a view not yet mounted gets three polls of grace. (S3) The gauge words what the runner really does: `handoffMode` (`src/econ/context.ts`) is the one predicate both call. `restart` = a hub task worktree, not a reviewer, chain not capped (three sessions), not a cascade step (`autoContinue: false`, read from the cascade state), limit above 0; `warn` = anything else with a limit (the hub may stop the run but starts nothing; the panel says to start a new session yourself); `off` = `contextLimit` 0. The API returns `handoff` and the EFFECTIVE `limit` (`RunManager.contextLimit`), and the levels, `turnsLeft` and the tick use it, not the constant. (N1) The slim SQL read checks `json_valid` first: a damaged row reads as an empty row. (N2) `run_event` has an index on `(run_id, kind, seq)` (created on open, idempotent), the size of a tool result is stored with it (`bytes`; older rows are measured), and a trace is built once per run and kept (8 per database) until the run writes another row (`MAX(seq)`); a turn row that is only UPDATED (a folded line, the cap below) does not move that mark, so a cached trace can lag by one row until the next event. (N3) Past 5000 turn rows no row is added, but the last one keeps following the newest call (and its time), so the gauge and the cache note do not freeze; the trace then shows the first 4999 calls and the last one. (N4) Folding looks only at the PREVIOUS turn row: interleaved messages (not seen from the CLI) would count as separate steps. At most 2000 tool calls wait for a result at once; beyond that a result is not matched and the tool shows «без ответа». (N5) Rules are the file the agent loads: `CLAUDE.md` for Claude, `AGENTS.md` for Codex (size only; a symlink counts 0 and `@AGENTS.md` imports are not followed, which is why the panel writes «≈»). A route's `headers` are filtered by `routeHeaders` to a validated `content-disposition` and nothing else, so the server's own `nosniff`, CSP and `no-store` cannot be replaced.

Consequences and trust boundary: the hub stores more rows per run, all of them numbers or the message id (no text from the model or a tool). The trace endpoint is a read of the hub's own database: it opens no file of any agent and no path from a request. The extra rows are bounded per run and per response. What can still be wrong: a CLI that reports wrong usage gives a wrong trace (same as ADR-018).

Status: red then green in `src/econ/context.test.ts` (breakdown sums, turnsLeft, levels, cache, window parsing and override, thread baseline, hostile answers), `src/server/trace-api.test.ts` (the context endpoint), `src/run/trace.test.ts` (build, paging, slim read, runner storage, cap), `src/run/trace-model.test.ts` (hostile data, filters), `src/server/trace-api.test.ts` (endpoints, download headers, re-redaction), `src/adapters/adapters.test.ts` (the extended `context` event). **Not verified live:** the real `stream-json` shape of `message.usage` and `message.id` on a signed-in CLI (the CLI on this PC is not signed in); that lines of one message really share `message.id`; whether `output_tokens` on a non-final line is partial. No real token numbers are claimed.

Known limits (accepted): per-step cost counts cache writes as input (the same approximation as the run cost); a step's time includes the tools it started and the model time of the next call; a trace of a run still in progress is a snapshot (reload to refresh).
