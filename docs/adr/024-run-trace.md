# ADR-024: the run trace and the context gauge read `turn` rows the hub stores per model call: numbers, names and times only, bounded everywhere

Context: Phase 7 shows what a run did step by step (tokens, prompt size, cache share, tool calls and their durations) and how full the context is while the user writes. Both need per-call numbers. ADR-018 deliberately did not store the per-call prompt size (the `context` event is only watched), and the `usage` event of a Claude run is the SUM of the run (the `result` line), so neither could answer "what did step 7 cost". The trace also must not become a second place where secrets or tool output live.

Decision (`src/adapters/claude.ts`, `src/adapters/event-utils.ts`, `src/run/runner.ts`, `src/run/trace.ts`, `src/server/api.ts`, `web/js/views/trace.js`, `web/js/trace-model.js`):
- **One parser.** The `context` event of ADR-018 stays the only place that reads `message.usage` of an `assistant` line (subagent lines, `parent_tool_use_id`, are still ignored). It now also carries the split of that call (`newIn` = input + cache writes, `cachedIn`, `out`) and the message id (`mid`), and is emitted FIRST in a line so that it opens the turn the line's tool calls belong to. The runner's watch (threshold, stop, warn) is unchanged.
- **What is stored.** The runner turns each `context` event into a `turn` row in `run_event` (numbers and the message id, rebuilt by `sanitizeEvent`: finite, whole, capped at 1e12). The Claude CLI writes one line per content block with the message's usage: lines with the same `mid` fold into one turn (the later line may carry the final `out`). A `turn` row is never sent to the panel stream and `RunManager.events()` leaves it out (the transcript, the chat log and the handoff card never see it); `seq` has a gap there, as it already has for `partial`.
- **Bounded storage.** At most `MAX_TURN_ROWS` (5000) turn rows per run; the first time the cap is hit the user gets one `warn` ("шагов больше 5000"). A hostile or runaway CLI cannot grow the log with them.
- **What a trace holds.** `buildTrace` reads `turn`, `tool`, `tool_result`, `usage`, `session` and `end` rows and returns names, numbers and times: per step the model, tokens, prompt size, cache hit `cachedIn / (newIn + cachedIn)`, price, and the tools (name, duration, ok, size of the output). It never returns a tool input or an output text. Tool names and the model are redacted AGAIN and capped at 100 characters on the way out (a row written before the sanitizer existed must not leak). `readTraceEvents` reads the rows with SQL that returns only the id and name of a tool and only the size in bytes of a result body: the 64 KB bodies stay in the database. At most 50 000 rows are read per trace (`truncated` says so); at most 100 tools are listed per step (`toolsMore` counts the rest); a page is at most 200 steps (`after` = last step number seen).
- **Honest numbers.** Durations are the hub's arrival times: a tool lasts from its call line to its result line, a step until the next step starts. That is inferred from the stream, not a stopwatch in the CLI, and the page says so. A tool with no result (the run was stopped) is marked `open`, never "ok". The price is `costUsd(model, tokens)` from the price table: an unknown model gives `null` ("неизвестна"), never 0; the run total is the CLI's own `total_cost_usd` when it reported one. A Codex run has no `turn` rows (no per-call prompt size is reported, ADR-018): a `usage` event closes a step and `context` is 0 = not measured. A run recorded before Phase 7 is one step holding what was recorded. Subagent calls are not in the trace (they are not in the `context` event either).
- **HTTP.** `GET /api/runs/:id/trace` (paged JSON) and `GET /api/runs/:id/trace.jsonl` (one JSON object per line: steps, then totals; `application/x-ndjson`, `content-disposition: attachment; filename="trace-<id>.jsonl"` with a validated id, `nosniff`). Same session cookie as every API call, GET only, id checked against `^r[0-9a-z]{2,40}$`. `Res` gained an optional plain-text body for the download; JSON stays the default.
- **Panel.** `trace.js` draws everything with `h()`/`textContent`; `trace-model.js` reads every field by type (never `String(x)`), turns control, bidi and zero-width characters into visible `\uXXXX` and caps names. The journal (`logs.js`) filters by project, agent, model and kind (`log-model.js`) and links each run row to «Подробно».

Consequences and trust boundary: the hub stores more rows per run, all of them numbers or the message id (no text from the model or a tool). The trace endpoint is a read of the hub's own database: it opens no file of any agent and no path from a request. The extra rows are bounded per run and per response. What can still be wrong: a CLI that reports wrong usage gives a wrong trace (same as ADR-018).

Status: red then green in `src/run/trace.test.ts` (build, paging, slim read, runner storage, cap), `src/run/trace-model.test.ts` (hostile data, filters), `src/server/trace-api.test.ts` (endpoints, download headers, re-redaction), `src/adapters/adapters.test.ts` (the extended `context` event). **Not verified live:** the real `stream-json` shape of `message.usage` and `message.id` on a signed-in CLI (the CLI on this PC is not signed in); that lines of one message really share `message.id`; whether `output_tokens` on a non-final line is partial. No real token numbers are claimed.

Known limits (accepted): per-step cost counts cache writes as input (the same approximation as the run cost); a step's time includes the tools it started and the model time of the next call; a trace of a run still in progress is a snapshot (reload to refresh).
