# ADR-018: a task run past 250K tokens of context is stopped and continued in a fresh session from its handoff card

Context: in a long session every model call carries the whole conversation. Past a few hundred thousand tokens each turn costs far more than the same turn in a fresh session that starts from a short card, and quality drops as the window fills. The hub already writes a handoff card for a usage limit (ADR-016/PR.4: facts from git and logs by code, a short story, no transcript), so the same card can carry a task over to a new session.

Decision (`src/run/runner.ts`, `src/run/handoff.ts`, `src/adapters/claude.ts`):
- **What is measured.** The size of the prompt of ONE model call: input + cache writes + cache reads (adapter event `context`). It is not the run total: the `result` line of `claude -p` sums every call of the run and would flag a healthy 30-turn session. The event is watched by the runner and never stored or sent to the panel (like `partial`), so a hostile CLI cannot grow the log with it; the adapter ignores non-finite, negative or non-numeric fields.
- **Threshold.** 250K (`CONTEXT_LIMIT`), taken from the Autopilot measurements the plan cites; not re-measured here. `RunManager({ contextLimit })` overrides it, `0` switches the watch off.
- **Why not compaction inside the CLI.** `/compact` and auto-compaction are the CLI's own summary of the transcript: a model call over the very context we want to leave, with no control over what is kept, no record of it in the hub, and no facts from git. The card is built by code from git (branch, changed files, checkpoint commit) plus the event log, is stored in `.hub/handoffs/`, and starts a session that carries only that card.
- **What happens.** First crossing: one `warn` ("контекст большой: начну новую сессию по карточке"), the agent process is stopped by the hub (outcome `context`, not `stopped`: the user did not stop it), a checkpoint commit and a card with `reason: context` are written, and `RunManager.handoff` starts a fresh run in the SAME worktree and branch with the same agent, model and effort. Permission is inherited as for any handoff: a review thread stays in `plan`, nothing widens.
- **Only where the hub owns the folder.** Automatic stop and restart apply to runs in a hub task worktree (`hub/<task>/<agent>`), the only place the hub commits a checkpoint (ADR-014). A chat in the user's own working tree gets the warning ("лучше начать новый чат") and is never stopped or committed for. Review-gate reviewers (`isolatedCwd`) are never touched.
- **Stop wins.** A Stop click before or during the restart always wins: a context line that was already buffered is ignored once the user stopped the run; and while the card is being made (the model summary can take up to 45 s) the run can still be stopped, which cancels the restart (the card is kept). The hub's own stop does not set the user's `stopped` flag.
- **Not inside a cascade.** A run the cascade starts has `autoContinue: false` (internal, never set from the HTTP API): at the limit it is stopped with its card, no continuation is started behind the cascade's deadline and run cap, and the cascade stops with the reason "context grew past the limit".
- **What the continuation carries.** The chain's original task text (not the previous handoff prompt), the task class and the estimate (so lean tool sets and econ keep working). The card goes into the prompt with its git facts as plain text and the written summary inside a random-nonce DATA block. Subagent calls (`parent_tool_use_id`) do not count toward the session's context. Runs stopped for context size are their own count in the outcomes table and stay out of effort and token estimates.
- **Bounded.** A chain is capped at three sessions stopped for context (the original and two fresh ones). The third is stopped too, its card is written, and the user is told ("уже три сессии подряд") to continue by hand. This prevents a task whose card plus first reads already exceed the limit from looping and spending quota without progress.
- **Codex.** Not covered: `turn.completed.usage.input_tokens` has not been verified to be a per-call prompt size (it may be summed over a turn), and a false stop would restart work for nothing. Codex keeps the usage-limit handoff only.

Consequences and trust boundary: the hub now starts a run without a click, in response to a number reported by the CLI. The blast radius is that of the run the user already started: same folder, agent, model, effort and permission, at most two extra sessions, in a hub-owned branch, never pushed. The prompt of the fresh session contains the card, which is redacted before it is written (the same path as the limit handoff). The card prompt names the reason, so the agent does not tell the user that a usage limit ended.

Status: threshold logic, stop, card, restart in the same worktree, the cap, the chat-only warning, the switch-off and the adapter parsing are tested with a fake agent (`src/run/run.test.ts`, `src/adapters/adapters.test.ts`). **Not verified live** (the CLI on this PC is not signed in): that the real stream-json `assistant` lines carry `message.usage` in the shape assumed, that 250K is the right threshold for the user's models, and the actual saving. No token numbers are claimed.

Known limits (accepted): on models with a 200K window the 250K threshold may rarely fire, because the CLI compacts on its own first. The `context` outcome label in the transcript for a continuation is recognised from the prompt text (the run row has no reason field).
