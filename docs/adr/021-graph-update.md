# ADR-021: the project graph is built by a bounded `graphify update` the user starts

Context: agents that ask the graph (`graphify query`) instead of listing and reading the repository save tokens (docs/TOOLING.md; the saving itself is not measured here). The graph is only useful if it exists and is not far behind the code, and the person should not need a terminal for that. Running graphify means starting an external program over the user's project, so the way it is started is a security decision.

Decision (`src/core/graph.ts`, `src/core/init.ts`, `src/server/api.ts`, `web/js/views/tools.js`):
- **Finding the tool.** `graphify` as an `.exe` / executable on an **absolute** PATH folder (relative entries such as `.` are skipped, so a project cannot supply it), else `python -P -m graphify`. `-P` keeps the working folder off the import path, so a `graphify.py` inside a project cannot replace the module (needs Python 3.11+; older Python means "not available"). Each candidate is accepted only after it runs `--help` from a neutral folder and prints a graphify usage line. The answer is remembered per PATH. `HUB_GRAPHIFY=off` switches the graph features off (the existing init/install/loading tests use it so they do not depend on the machine).
- **Starting it.** Argument array only (`[...prefix, 'update', <project root>]`), no shell. The root is an absolute folder of a project the user opened in the hub, never a filesystem root. Working folder: an empty throw-away folder under `<hub home>/tmp` (graphify also creates a `graphify-out` in its cwd; that must not be the project), removed afterwards. Environment: the same allowlist as git and review checks (`minimalEnv`): PATH, system and profile folders, no API keys, no hub tokens, no proxy settings. Timeout 10 minutes, then the process tree is killed. One run per project at a time (`409` for a second request). Output kept is the last 8 KB, redacted, 300 characters shown.
- **What it may change.** `graphify update` re-reads code files (no model, no network; observed on a throw-away project) and writes `<project>/graphify-out/`. That is a generated, separate folder, so it does not go through plan, backup and undo like the user's own files. The user still approves each run: `POST /api/graph/update` refuses without `approved: true`, and the panel asks first and says what is read and written. The result (ok, duration, last line) is appended to `<project>/.hub/audit.jsonl`, which is what the Journal shows.
- **`.graphifyignore`.** When graphify is available `hub init` adds a `.graphifyignore` to the plan (never replacing the user's own) that keeps secrets (`.env*`, `secrets/`, `.sandbox-secrets/`, `auth.json`, `.credentials.json`, keys), dependencies, build output, lockfiles and the graph's own output out of the graph. It goes through the normal init plan, approval and backup. Whether graphify itself honours every line is its behaviour, not verified here; the hub uses the same file only to decide what counts as stale.
- **Hardening (review fixes).** The `.graphifyignore` matcher is per path segment and linear (no regex: a hostile line cannot stall the status); lines over 200 characters or with more than 8 wildcards are dropped. `git ls-files` runs with `agentConfigGuard` (no fsmonitor program, no filters), `--no-optional-locks` and no untracked cache, because the task folder's git config is the agent's to write. Dependency folders are dropped before the 50,000-file cap. `.hub` and `graphify-out` that are links (symlink or junction) leading outside the project are refused for the update and for the audit line.
- **Status.** `built` / `stale` / `missing` = the modification time of `graphify-out/graph.json` against the project's files (git's own list in a repository, so `.gitignore` is respected, else a bounded walk that skips `.git`, `node_modules`, `graphify-out`, `.hub` and symlinks; at most 50,000 files), minus `.graphifyignore` (a gitignore subset: names, `dir/`, `*`, `**`, leading `/`; no `!`). A deleted file is not noticed.
- **Limits stated to the user.** `update` covers code only; documents and images are re-read by an agent with `/graphify . --update`, which can call a model. The hub never starts that.

Status: argument array, cwd, environment, timeout kill, single flight, redaction, audit line, status rules, init plan and the API are tested with a fake graphify (`src/core/core.test.ts`, `src/server/server.test.ts`). **Observed with the real graphify** (python module, this PC): the panel built the graph of a small throw-away git project through the confirmation, in about 2 s, and the status went missing, built, stale after an edit. Not verified: behaviour on a large repository, graphify on macOS/Linux, `.graphifyignore` handling inside graphify, and any token saving.

Known limits (accepted): the first `locateGraphify` lookup uses `spawnSync` (under a second here) and blocks the server for that time; a negative answer is cached for 60 s, a positive one until restart.
