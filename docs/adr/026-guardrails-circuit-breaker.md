# ADR-026: the circuit breaker stops runaway runs, is ON by default, and only the user's own config can loosen it

Context: an agent that loops on one failure, a continuation chain that keeps restarting, a run that burns a day's limit in an hour, or an unattended scheduler (ADR-025) are the ways the hub could spend a user's limit or money without anyone looking. The plan's task 7.5 also asks for review guardrails that tighten the review gate when accepted work keeps coming back. The danger of the protection itself is that something other than the user can turn it down: a `hub.json` from a cloned repository, a request body, a script that has the panel's cookie.

Decision (`src/run/breaker.ts`, `src/run/runner.ts`, `src/server/phase7-api.ts`, `src/review/guardrails.ts`, `web/js/views/guard.js`):
- **What it stops.** (1) One RUN over a token cap (weighted Mtok = uncached + 0.1 x cached + 5 x output, the econ `weighted`) or a cost cap (API-equivalent dollars): the hub stops the run as soon as the live totals pass it. (2) The DAY (rolling 24 h, all projects) over its token or cost cap: new starts are refused and live runs are stopped; it clears itself as the day rolls. (3) The same failure N times in a row in a project (equal normalised error text, no success in between, the last one less than 30 minutes ago): starts in that project are refused until the cooldown passes or the user acknowledges. (4) A continuation chain longer than `chainMax` runs: the next continuation is refused, a live run past the limit is stopped. (5) `stopsN` runs stopped for context size or a limit within an hour in one project: starts in that project are refused. The numbers are the author's, not measurements: per run 25 weighted Mtok / $40, per day 120 / $150, 3 failures, chains of 6, 4 stops. They are written next to the defaults in `breaker.ts` with what they are measured against (the default token profile: p90 about 5, median about 0.7 weighted Mtok).
- **Where it acts.** `RunManager.start` asks the guard FIRST (before a row, a worktree or a process exists) and a refusal is an `Error` with a Russian reason, which every caller already shows (the panel's toast, the CLI, a cascade, the scheduler's `failed-to-start`). A guard that cannot decide refuses the start. While a run works, every model call (`turn` row) and every `usage` event updates the live totals and asks the guard again; a "yes, stop" sets the run's outcome to `stopped` (it says nothing about the model's quality, so the router's statistics ignore it), emits one `warn` with the reason, and stops the process. A guard that THROWS while a run works is ignored: a bug in the protection is not a reason to kill work. The hub's own stop is not shown as "stopped by user".
- **ON by default, in the one place that matters.** `RunManager` builds `makeGuard` itself when no `guard` option is given, so every construction in the product (the CLI, the panel, the review gate, cascades, the scheduler) is protected. `guard: false` exists for tests that must not be limited and is not reachable from any request, file or config.
- **Who can change it.** Only `guardrails` in the user's own `<hub home>/config.json`, written by `POST /api/guardrails` from the panel (the same rule as ADR-025: cookie, Host, Origin, the same-origin Origin AND the panel's header; this proves the panel's code made the request, not that a human clicked, and a request with no Origin is accepted by routes that do not read `meta`). A number outside its range (`CAP_RANGE`, whose ceiling is now 3 times the default: 75 weighted Mtok and $120 per run, 360 and $450 per day, 9 failures, chains of 18, 12 stops; it was 10 times) is REFUSED with the field named, not clamped; the config is clamped into the range when read, so a hand-edited file cannot lift a cap past the ceiling. Switching OFF needs the typed word `ВЫКЛЮЧИТЬ` on top of that, only the boolean `false` counts (a string, `0`, `null` leave it ON), every change is appended to `<home>/guardrails-audit.jsonl`, and while it is off the Today page carries a standing warning. A project's `hub.json` may carry `guardrails` but only to TIGHTEN: per number the smaller of the two wins, a larger number is ignored and named in a note, `enabled` is ignored, the file is read only when it is a small regular file (never a link), and nothing is read from a request body of any run route (test: a body and a `hub.json` that both say "off" and "huge" change nothing).
- **Acknowledging.** The user can acknowledge a repeated failure or repeated stops (`same-failure:<project id>`, `repeated-stops:<project id>`): facts up to that moment no longer count for it. A cap, a chain or a day cannot be acknowledged away. The acknowledgements are `<home>/guardrails.json`, validated on read.
- **The state is derived, not stored.** `evaluate` is a pure function of the run table's last three days plus the acknowledgements and takes the clock as an argument; there is no trip list to get out of sync, and the tests use a fake clock and no timers. The scheduler asks the same breaker before every start, and the start is checked again by the RunManager.
- **Review guardrails.** `guardrails(window)` (pure) turns the last 14 days into `{ reviewEffort, humanFromTier, why }`: more than 10 % of accepted branches re-opened gives Deep effort and a human approval from the medium tier; more than 40 % of answered findings rejected as wrong flags the reviewer for `hub review-eval`. Under 5 accepted branches or 10 answered findings the rule does not fire (a few cases are not a rate; the answer says so). The result is SHOWN (Today, `GET /api/guardrails`); the review launcher does not read it yet (the plan lists no gate change), so it tightens nothing by itself.

Consequences and trust boundary: the trust root is the panel session, as in ADR-025. A local process that can forge both click headers could change the user's caps, within the ranges, and the change is in the audit file. The hub never raises a cap by itself. What the breaker cannot do: it sees only what the CLI reports (a CLI that under-reports usage defeats the token caps; the cost cap for Claude is estimated from the price table until the final cost arrives), it acts on the hub's own runs (not on an agent started in a terminal), and its numbers are not tuned to anyone's real usage.

Status: red then green in `src/run/breaker.test.ts` (defaults ON; only boolean `false` in the user config disables; `hub.json` tightens only and cannot disable; clamping and refusal; every trip kind at its threshold with a fake clock, cooldown, acknowledgement, project scope; the run table to facts; the guard; the RunManager refusing a start, stopping a live run over the cap (fake agent `claude-heavy`), surviving a throwing guard; a run request body plus a hostile `hub.json` changing nothing), `src/review/guardrails.test.ts` (thresholds at exactly 10 % and 40 %, minimums, hostile counts, the window from the tables), `src/server/phase7-api.test.ts` (the click rule, the typed word, ranges, acknowledgement, the real start route refusing).

Known limits (accepted, labelled): the default numbers are unmeasured; a run is stopped at the first model call that passes the cap, so it can overshoot by one call; Codex reports usage per turn, Claude per model call and at the end (the live Claude cost is an estimate); the day cap counts runs started in the last 24 h, including their later spend; the review guardrail's effort and tier are advice until the review launcher reads them.

## Review fixes (after the Opus review of 7.3-7.5)

- **A breaker stop is a failure, not an invisible stop.** The outcome is now `guard` (a new value). Quality, routing and the forecast treat it as `failed` (`settledOutcome` maps it, `runScore` 0): a runaway model looks worse. It counts in the same-failure streak (its own signature), and in `repeated-stops` next to `context` and `limit`: ten breaker stops in an hour now trip the breaker. The panel names it («остановлено защитой») in both label maps and the trace.
- **Chains are enforced.** `usage()` stops a live run whose continuation chain is past `chainMax`, not only the start of a new one.
- **Tamper evidence.** The `guardrails` part of `config.json` and the acknowledgements file are sealed by the hub's own routes (hash in `integrity.json`). A value that does not match is IGNORED: the defaults apply and the protection stays ON, forged acknowledgements clear nothing, the change goes once to the audit log and `tamper.json`, `GET /api/guardrails` lists it and the Today page says «Файл настроек изменён не hub: проверьте». `POST /api/integrity/reset` drops what those files held (caps to the defaults, no acknowledgement, scheduler OFF). `hub.json` notes ("hub.json asked for a higher cap and did not get it", "hub.json cannot switch the protection") are returned by `GET /api/guardrails` and shown in the settings card.
- **The push guard is a hook.** `pushGuardEnv` points `core.hooksPath` at a pre-push hook that refuses; `git push --no-verify` skips a pre-push hook. The guard stops an agent that pushes by habit, not one that is determined to; the hub never pushes itself.

### What an unattended agent can reach

Same statement as in ADR-025: an agent running as the user can write the hub's own files. Sealing `config.json`'s `guardrails` and the acknowledgements makes a naive change visible and keeps the protection ON, but an agent that rewrites `integrity.json` as well is not stopped. The breaker is a seat belt for runaway cost and loops, not a sandbox.
