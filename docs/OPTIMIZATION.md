## 1. Что взять из harness2

harness2 улучшает «обвязку» агента (промпты, ограничения, память, подсказки к инструментам, субагенты, скиллы, скрипты, плагины), не трогая модель. Сам фреймворк в v1 не подключаем (Linux, Vertex AI, отключённая песочница Codex). Берём механизмы:

| Механизм harness2 | Как это выглядит в панели |
|---|---|
| **Явная обвязка из 8 частей**, сгруппированных по роли (построение контекста, интерфейс инструментов, делегирование, промежуточный слой) | «Профиль обвязки проекта» в `hub.lock`: правила, ограничения, память, подсказки к инструментам, политика субагентов, скиллы, скрипты, плагины. Любое изменение — версия с diff, которую можно сравнить |
| **Пробы кандидатов на той же задаче** | `hub probe`: 2–3 варианта правки (например, «с graphify» и «без») прогоняются на одной замороженной задаче в отдельных worktree; сравниваются тесты, токены, время |
| **Композиция по контрастам поведения**, а не по одному прогону | правка к `AGENTS.md` или профилю предлагается только из разницы между прогонами («вариант B не перечитывал репозиторий и прошёл тест»), а не из рассуждений одного агента |
| **Инвариантные и предметные правки** | слои правил: глобальные инварианты → тип проекта (mobile, web) → конкретный проект. Новый урок помечается слоем, куда его можно поднять |
| **Улучшающая обвязка с уроками, подкреплёнными доказательствами** | `.hub/lessons/`: урок = наблюдение + правило + доказательство (ID запусков, diff, изменение метрики) + где подходит / где нет. Без доказательства урок не принимается. Это совпадает с вашими «reviewed lessons» в дизайн-пайплайне |
| **Рефлектор опыта после задачи** | этап 8: дешёвая модель (Haiku 5.5) пишет кандидата в уроки, вы принимаете или отклоняете |
| **Широкий (параллельный) и глубокий (последовательный) поиск** | по умолчанию последовательно (дёшево); параллельные пробы `k` только для правок с большим эффектом (правила, профиль скиллов) |
| **Бюджет `k` и `--dry-run`** | у каждой пробы бюджет попыток; `--dry-run` показывает план и оценку без вызовов моделей |
| **Оценка на тех же условиях** (тот же набор задач, исполнитель, сид) | золотой набор `eval/golden/` из 10–20 задач вашей истории; сравнение только на нём |
| **Возобновляемые прогоны** | папка запуска с журналом; повторная команда продолжает, а не начинает заново |
| **Изоляция оценки** (сеть закрыта, чтобы агент не нашёл ответы) | пробы запускаются в песочнице без сети, если задача её не требует |

## 2. Токены

1. **Двухуровневые скиллы.** Агент видит только профиль проекта (до 15 скиллов) плюс один скилл-указатель `hub-skill-index`, который по запросу ищет нужный скилл в полной библиотеке. Вместо ≈ 30 тыс. токенов описаний на ход — около 2–3 тыс. Проверить, как именно отключать плагины на уровне проекта в каждом агенте (часть 1).
2. **Стабильный префикс.** Порядок контекста: правила → скиллы → задача. В `AGENTS.md` нет дат, счётчиков и часто меняющегося текста. Каждое изменение `AGENTS.md` — через PR, потому что оно сбрасывает кэш у всех агентов.
3. **«Тихие» обёртки команд.** `hub test`, `hub lint`, `hub build` печатают итог и только падающие тесты с последними строками. Логи тестов — один из самых дорогих источников токенов в агентной работе.
4. **Сначала граф.** Агент читает отчёт graphify и идёт к нужным файлам, а не перебирает репозиторий. Один граф на проект, обновление только по изменениям.
5. **Детерминированное — скриптам.** Форматирование, генерация схем, токенов дизайна, конфигов — код, а не модель.
6. **Структурированные отчёты агентов.** Короткий JSON-статус (что сделано, тесты, файлы, вопросы) вместо прозы.
7. **Бюджет контекста на задачу.** Панель предупреждает на p75 и предлагает разбить задачу на p90 (≈ 25 млн токенов суммарно).
8. **Без субагентов по умолчанию**, параллельность через отдельные worktree.

## 3. Качество

1. **Золотой набор задач** — регрессия для любой правки обвязки (правила, профиль, модель по умолчанию).
2. **Метрика «с первой попытки»** по клеткам «класс задачи × модель × рассуждение»; советчик опирается на неё, а не на интуицию.
3. **Спецификация и тест до кода.** Дешёвая модель с чётким тестом приёмки справляется чаще, чем дорогая без него.
4. **Перекрёстное ревью другим классом модели**, только по diff.
5. **Честные статусы** (observed / inferred / proposed / approved) во всех отчётах — из вашего дизайн-пайплайна.
6. **Ворота этапов**: этап не закрывается без файлов-результатов и вашего «OK».

## 4. Память

Три вида памяти, все в файлах проекта, обоим агентам видны через `AGENTS.md`:

| Вид | Что хранит | Где |
|---|---|---|
| Смысловая | факты о проекте, решения, ADR | `AGENTS.md`, `docs/adr/` |
| Эпизодическая | что происходило: карточки передачи, итоги запусков | `.hub/handoffs/`, журнал запусков |
| Процедурная | как делать лучше: уроки с доказательствами, скиллы | `.hub/lessons/`, `skills/` |

- **Импорт существующей памяти** только на чтение: auto-memory Claude (`~/.claude/projects/*/memory`) и `~/.codex/memories` (там git-репозиторий с итогами сессий), с удалением дублей.
- **Подгрузка по релевантности:** в задачу попадают 3–5 записей, а не вся память.
- **Гигиена:** у записи есть область, источник и срок пересмотра; раз в неделю сводка «устаревшие и противоречащие записи» на ваше подтверждение.

## 5. Скорость

1. **Параллельность через worktree:** независимые задачи идут одновременно на разных агентах (Claude и Codex), каждая в своём контексте.
2. **Подготовка пока вы думаете:** пока вы подтверждаете задачу, панель создаёт worktree, делает sparse-checkout, обновляет граф и собирает пакет контекста.
3. **Тёплый кэш:** задачи одного проекта идут подряд, с тем же префиксом правил, чтобы попадать в кэш.
4. **Модель по задержке:** интерактивные шаги — Sonnet; Opus только на блокерах. Быстрый режим Opus (`/fast` в Claude Code) — когда время важнее цены.
5. **Расписание под лимиты:** тяжёлые задачи ставятся после сброса окна; панель показывает «лимит закончится через N задач».

## 6. Простота выбора скиллов, плагинов и MCP

1. **Пресеты по типу проекта** («web-saas», «mobile-app», «automation», «design-study»): один выбор вместо 300 скиллов.
2. **Скаут показывает не больше 5 кандидатов** с одной строкой «зачем», ценой в токенах, лицензией, совместимостью и риском.
3. **Автоочистка:** скилл, который не вызывался в проекте 30 дней, предлагается выключить. Данные уже есть: в `~/.claude.json` хранятся `skillUsage` и `pluginUsage`.
4. **Поиск дублей:** похожие по имени и описанию скиллы (как три копии Airflow) показываются вместе с предложением оставить один.
5. **MCP в одну команду** с подсказкой по OAuth (как для Mobbin) и проверкой подключения.
6. **«Почему это включено»:** для любого компонента `hub explain <id>` показывает, кто и когда его добавил и для какого этапа.

## 7. Выполнение самого проекта

1. **Вертикальные срезы:** каждая итерация даёт работающую вещь (после I1 — общий конфиг для Claude и Codex; после I2 — общая история).
2. **Собственная проверка:** панель с I1 управляет своей же разработкой (профиль, правила), с I2 — видит свою историю, с I3 — передаёт свои задачи.
3. **Ритм под лимиты:** в начале недели Opus планирует итерацию, в течение недели Sonnet исполняет; ревью в конце.
4. **Бюджет сессий на итерацию** и правило остановки; продление бюджета — только явным решением с записью (как в вашем V15).
5. **Definition of Done** для каждой задачи (PLAN, раздел 10).
6. **Сначала замер, потом оптимизация:** I0 создаёт золотой набор задач и меряет «как есть», чтобы любые улучшения были видны в цифрах.

## 8. Что проверить первым

| Гипотеза | Как проверяем | Когда |
|---|---|---|
| Профиль из ≤15 скиллов не ухудшает выбор нужного скилла | золотой набор, с полным списком и с профилем | I0–I1 |
| graphify снижает токены на навигации | A/B на 10 задачах | I1 |
| ponytail снижает токены на ~20% без потери качества | A/B на 10 задачах | I1 |
| «Тихие» обёртки команд снижают вход | сравнение до и после | I1 |
| Medium у Sonnet не хуже high на реализации | доля с первой попытки | I1–I2 |
