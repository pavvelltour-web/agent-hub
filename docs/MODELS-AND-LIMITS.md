Выводы:

- **57% всех токенов Codex ушло в субагентные треды**: 912 субагентных тредов против 106 основных, в среднем 7,3 субагента на основной тред, максимум 175. Поэтому субагенты по умолчанию выключены.
- **Уровень рассуждения не даёт ясной разницы в размере сессии** (медианы взвешенных токенов: low 0,76, medium 0,57, high 0,84, xhigh 0,97, ultra 0,65). Значит «выше уровень = лучше» нужно подтверждать долей задач, прошедших с первой попытки, а не размером.
- В 5 из 11 недельных окон процент доходил до 100%.

## 4. Почему процент недельного лимита нельзя пересчитать формулой

| Окно | Итог по логам на этом ПК | Взвешенных млн на 1% |
|---|---|---:|
| pro, 05–06 окт | 100% при 119,9 млн | 1,2 |
| pro, 15–16 окт | 70% при 191,8 млн | 2,7 |
| prolite, 18–19 окт | 100% при 819 млн | 8,2 |
| prolite, 20 окт | 95% при 92,9 млн | 1,0 |
| два изолированных запуска (pro) | 2–5% | 0,2–0,3 |

Разброс от 0,06 до 8 — более чем в 100 раз. Возможные причины: часть расхода идёт не с этого ПК и не из этих логов, окна в логах размыты, план менялся с `pro` на `prolite`, неизвестно, как лимит учитывает кэш и разные модели. Статического коэффициента получить нельзя.

**Решение для панели:** процент недельного лимита — диапазон с уверенностью «низкая», пока не накоплена калибровка; панель измеряет коэффициент по своим запускам и обновляет скользящим окном. Для планирования используется грубая рамка **1–8 взвешенных млн токенов на 1%** для плана `prolite` (неделя около 100–800 взвешенных млн). Это рамка, не измерение.

Для Claude Pro измерения нет. В первые две недели панель просит вас записывать процент из `/usage` до и после каждой сессии, пока не найдётся автоматический способ.

## 6. Распределение моделей (по вашему решению)

Основной агент — **Claude**: Opus 5.5 для плана и сложных архитектурных решений, Sonnet 5.5 для основной работы по плану, Opus подключается при затыке.

| Класс задачи | Модель | Рассуждение | Сессий | Что входит |
|---|---|---|---:|---|
| План, архитектура, ADR, решения по безопасности | **Opus 5.5** | high; максимум доступного только для 4 решений | 27 | 6 документов и планов, 5 дизайнов частей, 8 перекрёстных ревью (части 3 и 5, схема данных, угрозы T1–T10), 8 запасных на эскалации |
| Реализация по плану, тесты, правки, механика | **Sonnet 5.5** | medium по умолчанию; low для механики; high для отладки и кода процессов | 69 | 52 реализации, 10 тестов, 7 документации и механики |

Разбивка по итерациям — в [PLAN.md](PLAN.md), раздел 8.

Четыре решения «максимального» уровня: модель безопасности, формат данных и `hub.lock`, интерфейс адаптера, протокол передачи. Остальное — high.

Уровни рассуждения называю общими словами; какие именно значения доступны в вашей версии CLI, определит `hub doctor`.

### 6.1. Лестница при затыке (от дешёвого к дорогому)

1. **Sonnet 5.5, medium.**
2. Затык (триггеры ниже) → **Sonnet 5.5, high**.
3. Не помогло → **Opus 5.5, high** с карточкой передачи (не весь чат), чтобы он не перечитывал историю.
4. После решения возвращаемся на Sonnet с короткой карточкой.

Триггеры эскалации (значения по умолчанию, калибруются):

- один и тот же тест падает после двух попыток;
- более 25 ходов с инструментами без нового зелёного теста;
- изменение затрагивает границу безопасности (T1–T10): обязательное ревью Opus независимо от затыка;
- в спецификации обнаружена неоднозначность: вопрос к вам или к Opus на уточнение.

### 6.2. Почему не «всегда максимум»

В вашей истории размер сессии почти не зависит от уровня рассуждения, значит заранее не известно, что высокий уровень даёт лучший результат. Начинаем с таблицы выше и в каждой клетке «класс × уровень» накапливаем долю задач, прошедших с первой попытки. После 10 сессий на клетку советчик меняет рекомендацию.

### 6.3. Субагенты

Выключены по умолчанию (ARCHITECTURE, 4.8): 57% токенов Codex у вас ушло в субагентные треды. Допускаем только независимые подзадачи с небольшим контекстом и для ревью по diff.

### 6.4. Запасной вариант (моё предложение, решаете вы)

Claude Pro без дополнительного использования останавливается при исчерпании лимита. Поскольку передача работы Codex — сама функция панели, её можно использовать как запасной путь: когда у Claude закончился лимит, продолжает Codex `gpt-6.1-sol` с карточкой передачи. Это снимает риск остановки работы и проверяет функцию на реальной задаче.

## 8. Как держать расход в нижней части диапазона

1. **Одна задача — одна сессия — один worktree.** Сессии больше 25 млн токенов суммарно (около p90) разбивать.
2. **Короткий стабильный `AGENTS.md`**, детали в `docs/` по запросу: кэш не ломается.
3. **Один граф graphify на проект**, а не копия в каждом worktree.
4. **`ponytail` на реализации** (в `lite` на коде безопасности).
5. **Профиль скиллов под проект** (TOOLING, раздел 8).
6. **Без субагентов по умолчанию.**
7. **Лестница моделей**: Opus только при затыке и на планы.
8. **Перекрёстное ревью по diff**, а не по репозиторию.
9. **Sparse-checkout в worktree.**
10. **Карточка передачи** вместо повторного объяснения.
11. **Замер до и после** (TOOLING, раздел 4): мера принимается, только если доля задач с первой попытки не упала.

## 9. План калибровки (первые две недели)

1. Часть 2 (журнал) идёт сразу после части 1: панель получает ваши реальные данные.
2. Для каждой сессии пишем: модель, рассуждение, токены по категориям, изменение процента лимита (Codex автоматически, Claude вручную).
3. После 10–15 сессий пересчитываем коэффициенты и сужаем диапазоны.
4. Через 2 недели обновляем этот документ фактическими числами.

- Профиль токенов сессии Claude принят равным профилю Codex.
- Веса 0,1 для кэша и 5 для вывода — отношения цен API, а не правила учёта лимитов подписки.
- Цена GPT 6.1 Sol не сверена с первоисточником; цены `gpt-6-astra` и `gpt-6-luna` не известны; связь цен с лимитами Codex не проверена.
- Лимиты Claude Pro (размер окон, веса моделей) не измерены.
- Пороги эскалации (2 попытки, 25 ходов) — стартовые значения.
- Данные по Codex охватывают только этот ПК и только сохранённые сессии.
- Заявленные эффекты `ponytail` (код короче на 54%, токенов меньше на 22%) взяты из сторонних описаний бенчмарка автора, не проверены.
